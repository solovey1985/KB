# The course

## How LLMs behave: tokens, context, sampling, non-determinism

**Tokens: The Unit of Input, Output, and Cost**

Claude processes text in **tokens** rather than words or characters, with the exact character-to-token ratio varying by model and tokenizer. Everything passed to or generated by the model—including prompts, conversation history, tool definitions/results, and responses—is measured in tokens. Because tokens dictate both API billing and context window limits, developers should estimate costs and capacity in tokens rather than word counts.

**The Context Window: A Fixed Budget**

The **context window** is the maximum number of tokens a model can process in a single request, holding the system prompt, conversation history, documents, tool results, and output simultaneously. If the input exceeds this limit, the request is rejected with a validation error, whereas hitting the limit mid-generation stops the model early and returns partial output with a `model_context_window_exceeded` stop reason. To prevent long production sessions from filling up the window, applications must actively trim or summarize conversation history before each API call.

**Sampling: Why the Same Prompt Can Give Different Answers**

Language models generate text by **sampling** from a probability distribution of possible next tokens rather than picking a single fixed word, meaning identical prompts can yield varied wording. While settings like `temperature` traditionally adjust how repeatable or varied those choices are, the newest Claude models reject non-default sampling parameters (`temperature`, `top_p`, `top_k`) with a 400 error and rely on prompting to steer behavior instead. Even on models that accept `temperature: 0`, outputs become more consistent but are never guaranteed to be identical across calls.

**Non-determinism: What It Means for Testing and Evals**

**Non-determinism** means identical inputs do not guarantee identical outputs, making exact-text assertions unreliable when testing Claude features. Instead, developers should verify structural properties—such as valid parsing, required fields, or values within an expected range—and use **evals with a model-graded judge** to assess meaning. Because of this, evals serve as the standard approach for confirming feature accuracy.

## Model options and reasoning modes
### The Claude Model Family

The Claude family spans four tiers offering distinct tradeoffs across cost, latency, and capability:

| Tier | Primary Strength | Best Use Case |
| --- | --- | --- |
| **Haiku** | Speed & cost efficiency | Lightweight tasks fitting its capability envelope |
| **Sonnet** | Balanced performance | Default choice for most production workloads |
| **Opus** | High capability | Demanding work exceeding Sonnet's envelope |
| **Fable** | Maximum intelligence | Complex reasoning, coding, and agentic workflows |

Start with **Sonnet** as your baseline, scaling up or down only when evals demonstrate a quality gap or confirm acceptable trade-offs, and verify current model identifiers against the documentation at build time.

### Reasoning Modes

Model selection and **reasoning mode** are independent per-call levers—choosing a model picks the family tier, while reasoning mode determines whether and how deeply it thinks before answering:

* **Adaptive Thinking & Effort:** Current models use adaptive thinking tuned via an **effort setting** rather than the deprecated `budget_tokens` parameter (which triggers a 400 error on newer generations).
* **Display & Defaults:** Thinking content is omitted from responses by default on newest models unless summarized display is explicitly requested, and default thinking behavior varies by model.
* **When to Use:** Reasoning delivers value on complex, multi-step tasks, whereas it adds unnecessary cost to simple lookups or classification.

### How They Work Together

Because model selection and reasoning mode are independent controls, developers can mix and match them per request to balance speed, cost, and intelligence:

| Configuration | Behavior & Outcome |
| --- | --- |
| **Capable Model + Reasoning Off** | Delivers fast, direct responses without extra thinking overhead. |
| **Smaller Model + Reasoning On** | Spends additional tokens thinking through problems despite a lighter base tier. |
| **Capable Model + High Effort** | Pairs maximum model intelligence with deep reasoning for the most demanding tasks. |

Implementation mechanics for enabling reasoning and handling thinking blocks are covered in **Module 2**, while cost/latency/quality trade-offs for model selection are addressed in **Module 4**.

## Prompting modes: zero-shot, one-shot, multi-shot
### The three modes

Prompting modes determine how many worked input/output examples are included directly inside the prompt to demonstrate the exact response format:

| Prompting Mode | Examples Provided | How It Works |
| --- | --- | --- |
| **Zero-shot** | 0 examples | Provides only task instructions and asks for the result. |
| **One-shot** | 1 example | Pairs the instructions with a single input/output example. |
| **Multi-shot (Few-shot)** | Several examples | Uses multiple examples in the prompt to pin down the exact desired output shape when descriptions alone fall short. |

### The cost and quality trade-off

Adding examples consumes tokens and context budget on every request, requiring you to balance output precision against cost:

| Approach | When to Use |
| --- | --- |
| **Zero-shot** | Simple tasks where the expected output shape is already obvious. |
| **One-shot / Multi-shot** | Outputs requiring a specific structure, casing, or edge-case handling that text descriptions alone miss. |

One or two accurate examples usually resolve formatting issues faster than lengthy written instructions, following the core rule to use the minimal prompt needed for reliable results.

### Mode & Model Choice

Prompting mode and model selection act as complementary levers that should be tuned together to optimize cost and performance:

* **Leveraging Examples for Smaller Models:** Adding a few examples can enable a smaller, cheaper model to match the structured output of a more capable model running zero-shot.
* **Eval-Driven Tuning:** Start with the simplest model and fewest examples that pass your eval, scaling up capability or examples only when eval results demonstrate a gap.

## The technical substrate: SDKs, REST, streaming, async
### How a developer reaches Claude: SDK versus raw REST

Both raw HTTP REST calls and official SDKs connect to the exact same underlying API and models, differing only in developer convenience:

| Approach | How It Works | Key Advantage |
| --- | --- | --- |
| **Raw REST API** | Sends manual HTTP requests with an API key and JSON body, then reads the JSON response. | Works directly with any standard HTTP client without extra dependencies. |
| **Official SDK** | Wraps the REST API in a thin language-specific layer (e.g., Python, TypeScript). | Automates authentication, request building, retries, and response parsing to reduce boilerplate. |

**Module 2** builds directly on the official SDK and the Messages API atop this REST foundation.

### Synchronous, streaming, and real-time responses

Responses can be delivered in one complete payload or incrementally as tokens are generated, depending on latency requirements:

| Delivery Mode | How It Works | Best Use Case |
| --- | --- | --- |
| **Synchronous** | Waits for the entire response to finish generating before returning it in one piece. | Short outputs and background jobs where no user is actively waiting. |
| **Streaming** | Transmits response chunks incrementally over HTTP via **server-sent events (SSE)** so your code can display and reassemble them immediately. | Long responses or interactive UIs where users are watching in real time. |

**Module 2** covers how to safely consume streams and recover from mid-stream interruptions.

### Asynchronous patterns for high-volume work

Two asynchronous patterns handle high-volume workloads depending on whether you need real-time concurrency or lower-cost offline bulk processing:

| Pattern | Mechanism | Latency & Cost | Best Use Case |
| --- | --- | --- | --- |
| **Non-blocking Async (`AsyncAnthropic` / Promises)** | Uses `async/await` in Python (`AsyncAnthropic`) or standard Promises in TypeScript so the thread isn't blocked while waiting. | Returns in **real time** at standard per-token pricing. | High-concurrency applications that need to handle other work while waiting for immediate responses. |
| **Message Batches API** | Submits a large set of requests in a single call, returning a batch ID to poll for completion. | Up to **24-hour** turnaround in exchange for a **lower per-token cost**. | Offline pipelines, evaluation runs, and bulk jobs where cost matters more than speed. |
